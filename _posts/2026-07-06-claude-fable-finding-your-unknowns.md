# Claude Fable 5：Finding your unknowns 深度解读

> 来源: Anthropic / Claude Blog | [原文链接](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns) | 发布日期: 2026-07-06

## 1. 文章基本信息

- **标题**: A field guide to Claude Fable 5: Finding your unknowns
- **来源**: Claude Blog / Anthropic
- **链接**: https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns
- **作者**: Thariq Shihipar，Anthropic technical staff
- **发布日期**: 2026-07-06
- **阅读时间**: 约 5 分钟
- **主题**: Claude Code、Claude Fable、Agentic Coding、unknowns、blind spot pass、implementation notes

这篇文章不是一篇模型能力宣传文，而更像是一份 Claude Code / Claude Fable 的使用方法论。作者讨论的重点不是“模型能不能写代码”，而是：当模型已经足够强时，真正限制产出质量的，反而是人类能否清楚地暴露、管理和消化自己的未知。

## 2. 文章要解决的核心问题（论点）

这篇文章试图回答的问题是：**在使用越来越强的 AI 编程 Agent 时，如何主动发现并管理任务中的“未知”，从而让模型少猜、多协作，最终得到更可靠的结果？**

作者认为，Claude Fable 这类模型已经强到一个阶段：它完成任务的瓶颈不再只是模型能力，而是使用者是否能帮助它澄清问题空间中的未知。

换句话说，失败往往不是因为 Claude 不够聪明，而是因为人没有意识到自己没有说清楚什么。

## 3. 问题所处的背景上下文

文章开头用了一个经典区分：

- **地图**: prompt、skill、上下文、需求描述，也就是用户交给 Claude 的信息。
- **领土**: 真实代码库、业务约束、历史包袱、团队规范、用户体验、部署环境，也就是任务真实发生的地方。

AI Agent 工作时，实际上是在拿“地图”去探索“领土”。但地图永远不等于领土。两者之间的差距，就是作者所说的 **unknowns**。

当任务很小时，未知可能不重要。比如让 Claude 改一个函数名、写一个简单脚本，即使有些信息缺失，模型也能靠常识补齐。但当任务变成长周期、多步骤、跨模块的 agentic coding 时，未知会快速累积。Claude 每遇到一个未知，就必须根据它对用户意图的最佳猜测做决定。猜对了，任务顺利推进；猜错了，可能整个实现方向都偏掉。

这也是很多 AI 编程体验里的常见问题：

- Claude 代码写得很多，但方向不是你想要的。
- 它遵循了“最佳实践”，但不符合当前项目的特殊约束。
- 它过度实现，或者在不该抽象的地方抽象。
- 它做完后你发现自己其实要的是另一种产品形态。
- 它没有错，但你也不敢合并，因为你并不了解它到底改了什么。

作者的观点是：这些问题很多不是单纯靠更强模型解决的，而要靠更好的“未知管理”来解决。

## 4. 文章的核心观点

### 4.1 Agentic coding 的核心技能，是减少和规划未知

作者把未知分成四类：

1. **Known Knowns：已知的已知**  
   你明确知道、并且写进 prompt 的东西。比如：“我要新增一个登录按钮，点击后调用 `/api/login`。”

2. **Known Unknowns：已知的未知**  
   你知道自己还没想清楚的东西。比如：“我还不确定登录失败时应该如何展示错误。”

3. **Unknown Knowns：未知的已知**  
   你心里其实有标准，但还没有语言化；看到结果时才知道对不对。比如 UI 风格、交互手感、代码组织偏好。

4. **Unknown Unknowns：未知的未知**  
   你完全没意识到的问题、风险、历史约束或更优解法。比如某个旧模块里已有类似实现、某个边界条件会破坏当前设计、某个行业知识你完全不了解。

作者认为，优秀的 agentic coder 并不是没有未知，而是更擅长假设未知存在，并用系统化方式让 Claude 帮自己发现未知。

### 4.2 太具体和太模糊都会失败

文章提出一个很重要的平衡：

- 如果指令太具体，Claude 可能会机械执行，即使中途发现更好的方向，也不敢偏离。
- 如果指令太模糊，Claude 会用通用最佳实践填空，但这些最佳实践未必适合你的任务。

真正好的指令不是“把所有细节写死”，也不是“让 Claude 自由发挥”，而是明确告诉 Claude：

- 哪些地方已经确定；
- 哪些地方允许探索；
- 哪些地方如果遇到未知，需要停下来、记录或提出问题；
- 哪些决策可以由 Claude 保守选择；
- 哪些决策必须由人类确认。

这其实是一种“人机协作协议”的设计。

### 4.3 实现前，要用低成本方式暴露未知

作者给出了一组实现前的模式。

#### Blind Spot Pass：盲点扫描

当你进入一个不熟悉领域时，可以直接让 Claude 帮你找未知未知。

示例：

> 我准备在这个代码库里新增一个 auth provider，但我不了解 auth 模块。请帮我做一次 blind spot pass，找出我相关的 unknown unknowns，并帮助我更好地给你下 prompt。

这个方法的价值在于：你不需要先知道该问什么。你可以让 Claude 先帮助你发现“你不知道自己不知道什么”。

这非常适合：

- 接手陌生代码库；
- 进入陌生业务领域；
- 做从没做过的技术方案；
- 处理设计、视频、音频、视觉等难以语言化的任务。

#### Brainstorms and prototypes：头脑风暴与原型

对于那些“看到才知道要不要”的需求，作者建议先让 Claude 做多个方向的原型，而不是直接进入正式实现。

比如：

> 我想基于这些数据做一个 dashboard，但我没有视觉品味，也不知道可能性有哪些。请做一个 HTML 页面，给我 4 个非常不同的设计方向，我先反馈。

这解决的是 **unknown knowns**：你可能说不出自己想要什么，但你看到之后能判断。

这对 AI 编程尤其重要，因为正式实现一旦开始，修改方向的成本会变高。提前用 mock、HTML、假数据、静态页面做探索，可以避免 Claude 在错误方向上投入太多。

#### Interviews：让 Claude 采访你

当你已经做了一轮探索，但仍有模糊点时，可以让 Claude 逐个问题采访你。

关键提示是：

> 一次问我一个问题，优先问那些答案会改变架构的问题。

这句话很重要。它把 Claude 的提问从“泛泛澄清”变成“高杠杆澄清”。不是所有问题都值得问，最值得问的是那些会改变技术方案、数据模型、用户流程的问题。

#### References：给参考物，尤其是源码

作者特别强调：最好的参考不是截图，而是源码。

如果你喜欢某个库的行为、某个组件的结构、某个实现的语义，直接让 Claude 读相关代码，比口头描述更有效。

这背后有一个重要启发：**对 AI Agent 来说，可执行或结构化的参考物，往往比自然语言需求更高保真。**

### 4.4 实现中，要记录偏离和决策

即使计划做得很好，实现过程中仍然会出现 unknown unknowns。

作者建议让 Claude 维护一个临时文件，例如：

```text
implementation-notes.md
```

并要求：

- 如果遇到边界情况；
- 如果不得不偏离原计划；
- 如果做了保守选择；
- 如果发现某个假设不成立；

就把它记录下来。

示例：

> 保持一个 implementation-notes.md 文件。如果你遇到迫使你偏离计划的边界情况，请选择保守方案，把它记录到 Deviations 下，然后继续。

这个方法非常实用。它解决了一个常见问题：Claude 在长任务里会做很多隐含决策，而用户事后很难知道这些决策为何发生。

有了 implementation notes，用户可以在任务结束后快速理解：

- 原计划哪里变了；
- 为什么变；
- Claude 做了哪些默认判断；
- 下一轮应该如何修正 prompt 或方案。

这相当于给 AI Agent 的工作过程增加了“可审计性”。

### 4.5 实现后，要用解释和测验帮助人类真正理解变更

作者提出两个后处理方式。

#### Pitches and explainers：生成面向协作的说明材料

当你需要把结果发给团队、评审者或决策者时，可以让 Claude 把：

- 原型；
- 规格；
- implementation notes；
- demo；
- 关键决策；
- 风险点；

整理成一份可以直接发到 Slack 或文档里的解释材料。

这不是锦上添花。对于复杂变更来说，说明材料是交付的一部分。

#### Quizzes：让 Claude 考你

这是文章里很有意思的一点。

作者说，长时间使用 Claude 后，Claude 可能完成了很多你没有完全意识到的工作。仅仅读 diff 只能得到浅层理解，因为很多行为依赖既有代码路径。

所以他会让 Claude 给自己出测验，确认自己真正理解了改动，只有全部答对才合并。

示例：

> 我想确认自己理解这次变更。请生成一份 HTML 报告，解释改动内容、上下文、直觉和实现细节，并在底部给我一个测验，我必须全部答对后才合并。

这个做法的意义是：**AI 可以加速写代码，但不能替代人类对系统责任的承担。**

如果人类不理解变更就合并，风险只是被延后了。

## 5. 观点对应的论据和案例

文章最后用 Fable 发布视频的制作作为案例。

作者并不是视频专家。他只知道 Claude 可以通过代码编辑视频、转录内容、调用 ffmpeg，但不知道这些方法是否足够准确，也不知道如何处理颜色分级。

于是他没有直接让 Claude “做一个发布视频”，而是分阶段探索未知：

1. 先让 Claude 解释 Whisper 转录和 ffmpeg 剪辑是否能准确处理停顿和语气词。
2. 再让 Claude 用 Remotion 和转录文本做一个原型视频，验证“画面和台词同步”是否可行。
3. 当发现视频显得有些灰暗时，作者意识到这涉及 color grading，但自己不懂，于是让 Claude 先教他色彩分级，而不是盲目生成几个版本。

这个案例很好地说明了文章主旨：复杂任务不是靠一个超级 prompt 一步完成，而是通过一系列低成本探索，让人和 AI 共同发现问题空间。

## 6. 我的评价和启发

### 6.1 这篇文章真正有价值的地方

这篇文章有价值，不是因为它提出了某个新工具，而是因为它把 AI 编程从“prompt 技巧”提升到了“协作方法论”。

很多人使用 AI 编程工具时，仍然停留在：

- 给任务；
- 等代码；
- 看结果；
- 不满意就重试。

而这篇文章给出的方式更像是：

- 先让 AI 帮我发现我不知道什么；
- 再通过原型把隐性偏好显性化；
- 然后用计划对齐高风险决策；
- 实现中记录偏离；
- 实现后通过说明和测验完成知识回收。

这套流程的本质是：**把 AI Agent 从“执行器”变成“未知发现器”和“认知放大器”。**

### 6.2 对 Claude Code / AI Agent 工作流的启发

我认为这篇文章对使用 AI Agent 做工程有几个直接启发。

第一，未来的高效工程师不只是会写 prompt，而是会设计“探索—收敛—执行—复盘”的工作流。

第二，越强的模型越需要更好的上下文治理。模型能力越强，它能自主推进的距离越长；而推进距离越长，早期未知带来的偏差也越大。

第三，AI 编程中的很多失败，应该被看作需求澄清失败，而不是代码生成失败。

第四，好的 AI 工作流应该留下中间产物：

- blind spot report；
- brainstorm options；
- prototype；
- implementation plan；
- implementation notes；
- final explainer；
- quiz。

这些中间产物看似增加步骤，实际是在降低返工成本和审查成本。

### 6.3 我不完全认同或需要补充的地方

文章整体偏向个人高阶用户经验，适合能力强、判断力强、愿意深度协作的人。但在团队和企业环境中，还需要更多制度化补充。

比如：

- implementation notes 应该如何标准化？
- 哪些偏离必须阻塞实现？
- Claude 的自主决策边界如何定义？
- quiz 是否能接入 code review checklist？
- blind spot pass 的输出是否应该沉淀到项目文档？
- 多 Agent 并行时，不同 Agent 发现的 unknowns 如何合并？

如果要把这套方法用于团队工程，不能只靠个人习惯，而应该工具化、模板化、流程化。

例如，可以在每个复杂 AI coding task 中强制生成：

```text
/spec.md
/implementation-plan.md
/implementation-notes.md
/review-explainer.md
```

并把这些文件作为 PR 的一部分。

### 6.4 对中文开发者的具体建议

如果你正在用 Claude Code、Cursor、Codex、Gemini CLI 或其他 Agentic coding 工具，我建议把这篇文章的方法简化成五个固定动作：

1. **开工前问盲点**  
   “请先帮我找这个任务里的 unknown unknowns。”

2. **不确定时先做原型**  
   “先不要改真实代码，用假数据做 3 个方向让我选择。”

3. **实现前要计划**  
   “请先写 implementation plan，突出我最可能需要决策的部分。”

4. **实现中记笔记**  
   “遇到偏离计划的地方，写入 implementation-notes.md。”

5. **合并前考我**  
   “请解释这次改动，并出题确认我是否真正理解。”

这五步比单纯追求更长 prompt 更有效。

## 总结

这篇文章的核心不是“Claude Fable 有多强”，而是一个更重要的判断：

**当 AI Agent 变强以后，工程质量的瓶颈会从模型能力转移到人类对未知的发现、表达和管理能力。**

未来会用 AI 编程的人，不只是会给命令的人，而是能让 AI 帮自己发现盲点、探索可能性、记录决策、解释结果，并最终把自己带到更高理解层级的人。

这也是 agentic coding 和普通代码补全最大的区别：普通补全是在帮你写已知内容；Agentic coding 真正有价值的地方，是帮你探索未知空间。
