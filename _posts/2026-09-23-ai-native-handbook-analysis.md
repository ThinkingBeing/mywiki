# 解读阿里《AI Native 研发范式实践手册》：编码只占 20%～30%，可靠交付才是关键

## 2. 文章要解决的核心问题（论点）

**模型已经会写代码之后，大型企业怎样把 Agent 从「能出码」做成「可靠交付」？**

Coding 正在被解决（手册称约占链路 20%～30%）。从模型/Harness 能力到大企业 10x 效能，中间有三道 gap：完整 Agent 基础设施、可调用的工作流与组织知识、以及文化/人才/激励/协同。个体路径相对清楚，**团队路径非常复杂**。

## 3. 问题所处的背景上下文

手册把 2024–2026 写成一条行业轨迹：

- **Copilot 时代（约 2024 中）**：GitHub Copilot、Cursor、通义灵码——IDE 内补全，解决单点编码。
- **叙事转折**：Cognition Devin（2024.3）把「AI 软件工程师」推上台；能力当时有限，叙事已经变了。
- **Agentic 时代（2024 末–2025 上）**：MCP；Claude Code CLI 把 Harness 推向前台（行动—验证—纠错）；Codex CLI / Multi-Agent V2、Gemini CLI、Jules、Cursor Agent 模式。
- **模型侧（手册自称 2026 年中口径）**：SWE-bench Verified 从不足 30% 到约 80%；Terminal-Bench 2.1 上 Claude、GPT-5.6 Sol、Qwen3 等突破约 85%。Coding 被当成「正在被解决」。
- **企业侧刚需**：Claude Managed Agents（2026.5）、Microsoft Entra 把 Agent 当目录身份、MCP 授权走 OAuth 2.1、OWASP Agentic 威胁模型。运行环境、身份权限、可观测从可选项变成规模化前提。

阿里内部判断更硬：这场变革接近高级语言对软件工程的冲击；只靠模型自然溢出，撑不起 10x。因此手册的写法是：**三案例 → 五共性挑战 → 企业级基础设施全景**，而不是再写一本模型评测。

## 4. 文章的核心观点

### 4.1 人、系统、Agent 重新划边界，不是无人化

系统管状态 / 权限 / 规则（高确定性）；Agent 管分析、生成、约束内长程执行；人管目标、取舍、高风险决策和最终责任。排期从「人日」退出主流程，协调成本上移到目标定义、验证标准和发布门禁。手册引用 Anthropic 对约 40 万次 Claude Code 会话的分析：**用户约 70% 规划决策，Agent 约 80% 执行决策**——用来支撑这种分工，不是无人化。

### 4.2 三个案例：同一认识，三条演进路径

**AIDC 数字投手（Alibaba.com 广告）**

6 人小队做「数字投手」：自动诊断、优化投放。效能走了三阶段：

| 阶段 | 做法 | 卡点 |
|------|------|------|
| 超级个体 | 一人 3～5 个会话，夜间也能跑长程任务 | 消化障碍、复用障碍；产能锁在个人电脑和单会话 |
| 数字员工 | 云上运行时，产品 / 研发 / 评测 / 数据按统一结构产出 | 岗位孤立、质量不稳、没人主动认领；人变传令兵 |
| 云上 Scrum | 数字员工要有自己的「钉钉」；按业务域组织，来活即起线程 | 人收拢到两件事：把 Loop 卡在环境和验证上；找真需求 |

业务上不是纯 ReAct，而是拆成「经验 / 手脚 / 头脑 / 评测」：经验预计算成结构化处方，手脚给出可操作清单，头脑只在围栏内推理，评测用黄金用例 + 红线一票否决。上线后发现这只解决了「能不能做」，没解决「做得对不对」，于是补数据闭环：经验 Loop（策略约 10 天→2 天）、手脚 Loop（约 80% 核心能力 Skill 化）。增长机会发现仍高度依赖人。

**千问用增 Agent**

用 Agent 重构用户增长投放。三阶段：粗放验证 AI Coding → 标准化适配存量工程 → 提高 SDLC 覆盖。边际收益下降后，限制交付的是项目理解、边界和验证，不是会不会写代码。工程抓手四件套：Code Docs + Code Graph + Rules；需求追问沉淀为 Spec / Tasks；TDD 把正确性变成可观察反馈；TraceId 打通日志—状态—调用链。反思：工程师重心迁到问题定义、上下文、边界、文档和验证；跨栈「破界」让个体端到端负责；**AI 友好的基础设施会倒逼原来靠口头传递的知识结构化**。下一阶段不是扩大使用范围，而是把「个人会用 AI」变成「组织稳定交付」。

**万有无界（人机协作平台自身的研发）**

一个任务拆成三块闭环：上下文资产、工程执行环境、验证证据。评审用基于 Git 的可交互原型（近四版本约 80% 交互体验类需求这么接）；设计师在真实工程分支交付可交互页面；Workspace 判断端、改动类型和共享范围后再加载上下文；auto bug fix 强调现场采集（版本 / 入口 / 复现步骤 / 请求日志）。角色从「交接」变成「人做判断、Agent 做执行与记录」。痛点诚实：节点级已经能做完理解—实现—验证，但缺陷日清率没有本质变化（OCR 约 53%→最高 63%），因为触发和校验仍靠人。下一阶段要个人执行节点 + 团队调度层主动发现上下游状态。

### 4.3 五道共性挑战

**挑战一：主战场是环境与验证，不是再嵌一层 workflow**

沿既有 SDLC 做 workflow 化（手册点名 SDD、Agent Skills、Superpowers 多属这条）是过渡态——优化的是「人如何用 AI」，不是「AI 如何用研发环境」。类比电气化：先换电动机、传动轴还在，真正跃升是单元驱动后整厂重构。Agentic 的核心不是给模型更多决策权，而是让它**自主获得验证信号并持续推进**。Workflow 留下调度、权限、状态、审计和高风险检查。分层验证：秒级（编译 / 类型 / 单测）给高频迭代；分钟级（集成 / 契约 / 浏览器）覆盖真实行为；人工只留机器裁不了的（业务价值、体验、伦理）。Spec 区分**约束**（长期保存、尽量自动检查）和**假设**（允许按反馈改实现路径）。内部案例：某端用户动线编码约 1 小时，上线约 3 周。

**挑战二：平台必须从「给人点的网页」变成「给 Agent 的操作面」**

Aone 这类统一 DevOps 平台曾经是规模化红利，现在 Agent 模拟人点 Web UI 会崩。三个硬问题：进不去、上下文不确定、工具只展示不推进。MCP 解决「怎么调工具」，不解决「该操作哪个对象」。建设名为 **al 的 CLI**——不是把网页搬进终端，而是稳定进入、稳定理解、稳定推进；手册称每天被数万工程的 Agent 使用。

**挑战三：度量对象是新生产系统，不是插件安装率**

不要围着「多少人用了 AI、AI 写了多少行」转。采集：多工具轻量 Hook → 标准事件 → 研发事实 → `Session → Commit → Change → Workitem` 归因。三层：

- **L1 AI 效能**：覆盖 / Session / Token / 采纳行 / Skill / MCP / 上下文资产
- **L2 工程质量**：缺陷、回滚、自修复、风险
- **L3 价值交付**：需求周期、变更周期、发布频率、AI vs 非 AI 对比

只看 L1 会「为了 AI 而 AI」。上下文资产（Skill / MCP / Spec / README / checklist）必须进指标，否则永远停在「每个人临时问 AI」。度量还要前移到 Agent Loop：定义、边界、SOP、权限、I/O 契约、验收和失败策略。

**挑战四：数字员工是新主体，主体模型变了**

Agent 同时踩人、应用、服务账号三类边界。协同三阶段：完全辅助 → 云端自主 → 多 Agent 协同，实质是信任边界外移。两条落地路线：组织虚拟员工（工号、进团队钉群）；原生 Agent 身份 + 复合令牌 + Credential Broker + 渐进授权。步骤：可见可管理 → 可控可复用 → 更高自主。终局不是每人一个助手，是一支可管理的数字员工队伍；身份技术解决不了组织责任。

**挑战五：组织从 org chart 转向 execution graph**

接住 Ken Huang 的判断：节点是人、Agent、数据、权限、工具、审批；关系从「谁向谁汇报」变成 routing + governance。人既是协作瓶颈，也是协作的隐性兜底（不完整需求、口头潜规则靠人补上）。可实践：专业岗合并、3～5 人小团队、管理者从信息中转变成意图教练、激励更高频、新老业务分治。

转型代价写得少见地狠：知识蒸馏结构上接近替代；入门岗断裂会抽空 senior 池；东外焦虑会让人藏隐性约定，而 Harness 恰恰需要这些约定被说出来。没有完美方案，但要明确红利是扩张边界还是收缩编制，评价必须从产出量改到判断质量。

### 4.4 企业级基础设施：五问，以及怎么拦

纲领五问：

1. Harness 让 Agent 能跑完长任务（上下文、计划、恢复、工具反馈、人机交接）
2. 知识库 + Skill + MCP/CLI 变成可在正确时机选对的能力，不是「接入多少工具」
3. Sandbox / Coding 环境把工具链、依赖、配置、数据、网络、验证一起声明
4. Identity / Policy / Guardrail 是硬约束，不靠模型自觉
5. 可观测对象扩展到完整 Trajectory

产品名（Qoder、al CLI、OpenSandbox、Aone Ground、Guardrail）是阿里承接位；可带走的是机制。

**Harness**

最小单元是持续闭环：目标 → 上下文 → 规划 → 工具 → 观察验证；未完成则下一轮；歧义或高风险转交人。四职责：上下文管理（按需加载、旧规则会冲突）、规划与恢复、工具—验证—纠错、人机协同。企业外层分程序性机制（Rules、AGENTS.md、CLI、Codemod、拦截 Hook）和模型推理机制（Skill、检索、Subagent、Review Agent）。必须严格执行的门禁走程序控制，不能只靠提示「记得遵守」。安全：输入侧 Prompt 防火墙只是第一道；行动前按身份、委托、资源、敏感级动态审查；最小权限短期凭证；高风险必须可阻断、可中断、可恢复、可审计、可逆。

**企业知识库**

四个作用：领域世界模型；知识外置（可更新/撤回/分级，不像权重）；给行动提供「何时做、依据什么、何时停」；可共享可审计的组织记忆。链路是 **整理 → 加工 → 治理 → 供给**。供给不止 RAG：结构化查询、下到本地文件系统用搜索、连实时业务系统。引用 Google **OKF**（Markdown + YAML frontmatter）——价值在元数据规范。治理必须吃 Agent 反馈（引用撑不住、频繁无答案、用户纠错），否则知识库静默腐烂。

**MCP / Skill / CLI**

| 能力 | 回答的问题 |
|------|------------|
| MCP、CLI | 怎么查询、操作、验证外部世界 |
| Skill | 这类任务应该怎么做（步骤、边界、完成标准） |

CLI 没有发现机制，必须配 Skill 告诉何时调用。MCP 有 OAuth 2.1；企业 CLI 还要把登录、短期凭证、命令级权限、高风险确认做成体系。评测两个数：**命中率**（有没有选对）和**成功率**（选对后能不能用对）。过大 MCP 要拆，长期低命中要删。

**Sandbox**

容器只解决「在哪跑」。生产级还要声明镜像与配额、TTL、命令与文件边界、出站白名单、凭据不进 Agent、暂停/快照、失败现场。四条边界：生命周期控制面（含 TTL 回收孤儿实例）；实例内执行面（结构化退出码和日志）；网络默认拒绝；凭据侧车（占位值，匹配域名/路径/方法后再注入，快照不含凭据）。点名 **OpenSandbox**（捐给 AAIF）。示例把 API Key 塞进环境变量，正文立刻说生产必须走代理注入。

**Coding 环境**

仓库不是完整交接。「代码改对了，项目跑不起来」是第一类问题：缺工具链、关联仓、配置、schema/种子数据、桩 vs 真上游、失败后看哪类证据。虚构电商例子：改取消窗口 → 缺配置 → schema 没字段 → 库存调用被拒——开发者本机修得了，下一个空实例会再踩一遍。原则：环境定义长期维护，实例随任务创建；**任务是状态边界**；通过验证的配置/数据/桩才进基线；再从干净实例复验。内部实现点名 **Aone Ground**。SWE-bench / SWE-agent 的 ACI 用来论证：通用 Linux 只是起点，企业语义不会随基础镜像出现。

**Identity**

传统应用权限不够：控制流到运行时才确定。要拆开 **认证、委托、策略授权、下游凭证**，不能合成一张万能 Token。角色：可信 Runtime、PDP、PEP、Credential Broker。原则：复合身份；权限逐级收敛（用户权 ∩ Agent 上限 ∩ 平台策略 ∩ 本次委托 ∩ 运行时约束）；靠近资源再鉴权（MCP 登录 ≠ 每个 tool 已授权）；长期凭证不进 Agent（代理调用 > 短期凭证 > 长期密钥）；可撤销可追溯。缺权第三态 **Challenge**：结构化说明谁确认、怎么确认；模型只看到「等待确认」，碰不到授权码。生产重启不能由 Agent 自己点头。

**Guardrail（安全生产）**

生产发布原则没变（可观测、可灰度、可回滚），变的是保障方式。已用于内部代码/配置分批 resume。

`GuardrailRun = Spec@revision/digest + ChangeSet@digest + 递增 Submission`。Agent 按固定 Spec 查证据，提交 **PASS / BLOCKED / UNKNOWN**；Guardrail **不解释业务含义**，只验收协议并机械聚合。有 BLOCKED 或 UNKNOWN 就不能放行；UNKNOWN 不许被当成 PASS。现场变了，旧结论失效。发布系统执行前还要自己终检状态、权限、目标和防重。规则维护者对口径负责；Agent 决定怎么调查，不能改检查目标。

**可观测**

传统 RED/USE 只回答系统正不正常。还要回答：为什么这样走、任务完成没有、是否偏离意图。对象：`Session → Task → Trajectory → Step`（Model Call / Tool Call / Skill / State Change / Outcome），用 Trace Context 把行为和系统 Trace 钉在一起。采集对齐 OpenTelemetry GenAI Semantic Conventions 和 **ATIF**。分析用级联漏斗：规则全量筛 → LLM 灰区 → 意图/推理/工具/检索。Trajectory 同时喂评测。SkillRuntime 把遥测封进执行环境，业务侧少埋点。

### 4.5 总结章自己承认什么

这是几个月的阶段性切面，**不是成熟方法论**。情绪曲线：兴奋（研发很快能托管）→ 务实（环境、上下文、验证、发布都卡）。未解决问题四条：交付最后一公里对隔离/凭证/Guardrail/可观测的要求远超当前；知识仍停在「人能查到」；组织没有标准答案，蒸馏焦虑会卡住知识沉淀；不要因为「等更好的模型」推迟基建。落款作者 OCR 不清，对外口径以「阿里技术」为准。

## 5. 观点对应的论据

| 观点 | 手册给出的证据 | 可信度注意 |
|------|----------------|------------|
| Coding 不是瓶颈 | 内部粗算编码占 20%～30%；某端用户动线：编码 1 小时，上线约 3 周 | 案例级，非全集团普查 |
| 模型 Coding 已很高 | 2026.7 快照表：Mythos 5 SWE-bench Pro 80.3% / TB 88.0%；GPT-5.6 Sol 64.6% / 88.8% 等 | 手册自写「口径不一，仅供参考」；OCR 模型名可能有误 |
| 云上 Scrum | 策略 10 天→2 天；约 80% 能力 Skill 化 | 单团队，缺对照实验 |
| 千问用增 | 「平均交付周期缩短一半」；缺陷相关数字 OCR 严重损坏 | 不要当精确数字引用 |
| 万有无界 | 交互需求约 80% 走 Git 原型；视觉一次修复约 89%；6–8 月调用超 2 万；线上缺陷率 OCR 为「千分之 0.01」；auto bug fix 约 60%，日清率 53%→63% | 统计范围需对照原图 |
| 平台 | al CLI「每天数万工程的 Agent」 | 量级宣传，无公开方法学 |
| 人机分工 | Anthropic ~40 万会话，约 70% / 80% | 单一产品样本，手册自己承认 |
| Guardrail | 已用于内部代码/配置分批 resume | 机制清楚，效果数字几乎没有 |
| OpenSandbox | 捐给 AAIF 的开源沙箱 | 产品位；架构原则可独立验证 |

三案例 complementary：AIDC 偏业务 Agent + 组织形态；千问用增偏存量工程 AI Coding 与 SDLC；万有无界偏协作平台自身的研发流程。

## 6. 我的评价和启发

**可信度**

大厂一线实践手册，不是评测论文。强项是失败模式和阶段演进（超级个体的消化障碍、数字员工变传令兵、架构「能做」但业务不对、workflow 化是电力轴传动、知识蒸馏的负面循环）。弱项是数字口径混杂、产品位和通用工程纪律缠在一起——通用纪律该留下，Qoder / al CLI / Aone Ground / OpenSandbox 该分开看。总结章比正文诚实，这反而加分。

**认同**

- 「编码被解决得越彻底，编码之外越成为瓶颈」和 Anthropic *AI-Native SDLC playbook*、以及「个人提效很大、交付周期几乎不动」这类组织观察是同一件事。
- 「确定性下沉工程、推理只发生在可控空间」就是 harness engineering：数字投手的经验/手脚/头脑，几乎是「AI 决策、脚本执行」的业务版。
- 度量三层和「上下文资产进指标」说对了激励扭曲。
- 组织代价那一节比大多数白皮书狠：不说清楚红利分配，Harness 需要的隐性知识会被藏起来。
- 后半最值得留下的三块：**环境定义 + 干净实例复验**；**Identity 四件套 + Challenge**；**Guardrail 三态协议**（生产自动化不必放松安全）。

**保留**

- 「专业岗没有太大意义」对绿场可能对，对资金、广告扣费、权限核心链路过激。手册自己在数字投手里把评测红线和人的发布门禁留得很死，和「破界」并置，执行时要按爆炸半径分层。
- SWE / Terminal-Bench 高分 → 生产交付，手册也承认不等价，但开篇仍用 benchmark 给「Coding 已解决」打气。
- 「云上 Scrum 不用日会 / 排期」依赖任务定义已经清楚。增长机会发现仍高度依赖人——转述时经常被砍掉。
- al CLI「数万 Agent」证明有入口，不证明任务完成率。挑战二写得很准：工具要返回「这意味着什么、下一步可以做什么」。

**对照已有解读，这份手册真正新增的**

已重合、不算新：代码不是瓶颈；要验证闭环；Agent = Model + Harness；确定性脚本/护栏。

真正新增：云上 Scrum / 数字员工主体模型；Aone → al CLI 的平台改造；L1–L3 度量并把上下文资产当指标；组织蒸馏的负面循环；OKF 式知识治理；环境作为第一类上下文并可复验；Guardrail 三态门控；Trajectory 行为可观测。
