## 2. 文章要解决的核心问题（论点）

如何让 LLM 构建一个持久、累积的个人知识库，而不是每次查询都从零开始"重新发现"知识？

## 3. 问题所处的背景上下文

- **现有方案的局限**: 大多数人与 LLM 和文档的交互方式是 RAG —— 上传文件，检索相关片段，生成答案。但 LLM 每次问题都要从头发现知识，没有累积。问一个需要综合五份文档的微妙问题，LLM 每次都要找并拼接相关片段。Nothing is built up.
- **问题起源**: NotebookLM、ChatGPT 文件上传、大多数 RAG 系统都是这种方式
- **灵感来源**: Vannevar Bush 的 Memex (1945) —— 个人策划的知识存储，文档间的关联本身就和文档一样有价值

## 4. 文章的核心观点

**核心观点**: LLM 增量构建和维护一个持久的 wiki（维基），作为你和原始资料之间的中间层。知识编译一次，然后保持最新，而非每次查询重新推导。

### 关键观点一：Wiki 是持久累积的产物

- 交叉引用已经存在
- 矛盾已经被标记
- 综合已经反映了你读过的所有内容
- 每次添加来源和提问，Wiki 都会变得更丰富

你从不（或很少）自己写 Wiki —— LLM 写作和维护一切。你负责来源、探索、提出正确的问题。

### 关键观点二：三层架构

**Layer 1: Raw sources（原始资料）**
- 你策划的源文档集合：文章、论文、图片、数据文件
- 不可变的 —— LLM 读取但不修改
- 这是你的真相来源

**Layer 2: The wiki**
- LLM 生成的 markdown 文件目录
- 摘要、实体页、概念页、比较、概述、综合
- LLM 完全拥有这一层：创建页面、更新、维持交叉引用、保持一致

**Layer 3: The schema**
- 一个文档（如 CLAUDE.md 或 AGENTS.md）
- 告诉 LLM wiki 如何构建、约定是什么、摄入来源/回答问题/维护的工作流程
- 这是关键配置文件 —— 让 LLM 成为有纪律的 wiki 维护者而非通用聊天机器人
- 你和 LLM 共同演进

### 关键观点三：三种操作

**Ingest（摄入）**
- 你放一个新来源到原始集合，告诉 LLM 处理它
- 示例流程：LLM 读取来源，与你讨论要点，写摘要页，更新索引，更新相关实体和概念页，追加日志
- 单个来源可能涉及 10-15 个 wiki 页面

**Query（查询）**
- 你基于 wiki 提问
- LLM 搜索相关页面，读取并综合答案，附带引用
- 答案可以是不同形式：markdown 页面、比较表格、幻灯片 (Marp)、图表 (matplotlib)、canvas
- 重要洞察：好的答案可以存回 wiki 成为新页面

**Lint（检查）**
- 定期让 LLM 做健康检查
- 查找：页面间的矛盾、被新来源取代的过时声明、孤立页面（无入站链接）、重要概念提及但缺页面、缺失交叉引用、数据空白

### 关键观点四：索引和日志

**index.md** —— 内容导向
- wiki 中所有内容的目录，每个页面列出链接、一行摘要
- 按类别组织（实体、概念、来源等）
- LLM 每次摄入时更新
- 查询时 LLM 先读索引找到相关页面，然后深入
- 在中等规模（~100 来源，数百页面）效果出奇好

**log.md** —— 时间顺序
- 只追加的记录：发生了什么、何时发生
- 摄入、查询、lint 通过
- 技巧：每个条目以一致前缀开头，可被简单 unix 工具解析

## 5. 观点对应的论据

| 观点 | 论据 |
|------|------|
| Wiki 累积价值 | 交叉引用已存在，矛盾已标记，综合已完成，无需每次重新推导 |
| LLM 维护成本低 | 枯燥的是维护工作（更新交叉引用、保持摘要最新）而非阅读或思考，人类放弃 wiki 是因为维护负担增长快于价值 |
| 适用场景 | 个人目标/健康/心理学、研究深度话题、读书笔记、商业/团队内部 wiki、竞争分析、尽职调查 |

## 6. 我的评价和启发

### 可信度评估

- 高可信。Andrej Karpathy 是 AI 领域顶尖专家，曾在 OpenAI、特斯拉工作
- 这是他设计的实际工作流程，非理论空谈
- 与他之前关于 LLM prompt 的文章风格一致

### 认同与不认同

**认同**:
- "Wiki 是持久累积产物"这个概念非常强大，解决了 RAG 的核心痛点
- 三层架构清晰易实施
- 与 Vannevar Bush Memex 的联系很有深度
- "LLM 是程序员，Obsidian 是 IDE" 的比喻精彩

**不认同/需观察**:
- 长期来看 wiki 质量如何保证？LLM 是否会累积幻觉？
- 多用户协作场景未充分讨论
- 规模化（上千来源）后的性能？

### 对我的启发

1. **知识管理范式转变**: 从"检索"到"累积"
2. **人机协作模式**: LLM 负责枯燥的维护工作，人负责思考和提问
3. **Git 版本控制**: Wiki 就是 git 仓库，免费获得版本历史、分支、协作

### 可以进一步探索的方向

- 如何检测和修正 wiki 中的 LLM 幻觉
- 规模化后的索引策略
- 与现有工具（Notion/Obsidian）的集成
